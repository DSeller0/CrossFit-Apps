# RLS probe — 2026-07-03 (anon write surface on results_v2 + class_executions)

The deferred security probe from [plans/04 step 6](../plans/04-dev-environment.md) and backlog **#7**. Run against the **local** Supabase stack (never prod), using the public anon key exactly as the browser holds it — `curl` against the local PostgREST endpoint, no authenticated session. Local policies are a faithful reproduction of prod (same migration), so these results describe prod's real posture.

## Method
Anon key only (no auth). For each verb: hit `http://127.0.0.1:54331/rest/v1/<table>` and check both the HTTP status and whether the row actually changed (via a follow-up read + a service-role cross-check). A tampered `results_v2` row was restored afterward with `seed-dev.mjs`.

## Findings

### results_v2 — anon can tamper with any athlete's result
| Verb | Result | Meaning |
|---|---|---|
| UPDATE any row (blocks / energy_level / coach_note / presence / flag_for_review) | **204, persisted** | Any visitor can overwrite **any** athlete's logged result — including coach-only fields `coach_note` and `flag_for_review`. |
| UPDATE `athlete_id` on a row | **204, persisted** | A result can be reassigned to a different or bogus athlete id. |
| INSERT with client-chosen `id` + `athlete_id` | **allowed** (intended self-log path) | Nothing binds the insert to the acting athlete — a visitor can forge a result under any athlete's id. |
| DELETE | **204 but row survived** | Blocked — RLS silently filters the row out of the delete scope (no permissive DELETE policy for anon). |

### class_executions — anon can rewrite any class, not just their check-in
| Verb | Result | Meaning |
|---|---|---|
| UPDATE any row (athlete_ids / anon_names / anon_results / groups) | **204, persisted** | A visitor can wipe or forge the roster, guest results, and rotation groups of **any** class — the `using(true)` policy is not scoped to the class the athlete is checking into (Schedule.jsx only ever means to append one id/name to the current check-in row). |
| DELETE | **204, row survived** | Blocked (RLS filter). |
| INSERT a forged class row | **401** | Blocked — only `public UPDATE` exists, no `public INSERT`; class creation is coach-only (`is_allowed_user()` via TvController). |

## Root cause
The public write policies are `using(true) with check(true)` — no **row** scoping and no **column** scoping. Because athletes are **not authenticated** (no login on public pages — deliberate, per the auth decision), RLS has no identity to scope against: the policy must permit the legitimate anon path (an athlete logging their own result, or checking in), and with `true` that same permission covers every other row and column. This is a structural limit of "anon writes with no athlete identity," not a policy typo.

## What's actually exposed vs. accepted
- **Genuinely dangerous:** cross-athlete/cross-class *overwrite* — a single visitor with the (public) anon key can corrupt the whole gym's results and rosters for a day, and can flip coach-only fields (`coach_note`, `flag_for_review`) that the UI implies only a coach controls.
- **Bounded:** no anon DELETE, no anon INSERT of forged classes. Damage is overwrite/append, not deletion or unbounded row creation. Coach edits still go through the `is_allowed_user()` path.
- **Threat model:** single private gym, low traffic, no adversary today. This is latent risk, not an active incident — but the anon key ships in the client bundle, so it's discoverable by anyone who opens dev tools.

## Recommendation
Tracked as the fix plan [plans/05-anon-write-hardening.md](../plans/05-anon-write-hardening.md). Short version: the proportionate fix is to move the two legitimate anon mutations behind `SECURITY DEFINER` RPCs (same pattern as `submit_pr`/`clear_pr`) that encapsulate exactly the allowed change, then revoke direct anon UPDATE on both tables — this removes arbitrary-row/column tampering without requiring athlete auth. Full per-athlete auth (#30/#31) remains the only thing that closes forged-*insert* identity, and stays a separate, heavier track.
