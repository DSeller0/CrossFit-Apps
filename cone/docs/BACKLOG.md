## ✅ Done (recent)

**2026-07-03 — #7 Anon write hardening (results_v2 + class_executions)** · `supabase/migrations/0003_anon_write_rpcs.sql` — two SECURITY DEFINER RPCs (`class_checkin` append-only roster join, `log_result` upsert on `UNIQUE(athlete_id, session_id)` that never touches `coach_note`/`flag_for_review`) replace the four anon `.update()`/`.upsert()` call sites in `Schedule.jsx` (check-in, self-log, desktop-reg) and `Results.jsx` (self-log) · `REVOKE INSERT, UPDATE ... FROM anon` on both tables · a `/security-review` pass before pushing caught that this alone was bypassable: the pre-existing `"public result insert"/"public result update"/"public update"` policies (`using(true) with check(true)`) had no `TO` clause, so they applied to *every* role, not just `anon` — and this app's OTP signup is open to any email (`is_allowed_user()` is enforced by policy, not by signup), so an attacker could self-serve an `authenticated` session and PATCH any row directly, fully bypassing the new RPCs. Confirmed live against the local stack (signed up `attacker@example.com`, got a valid `authenticated` JWT, successfully overwrote `coach_note` pre-fix) before dropping the three stale policies — SECURITY DEFINER functions bypass RLS regardless (owner has BYPASSRLS), so dropping them doesn't affect the RPCs, and `"auth write"` (`is_allowed_user()`) remains the only direct-table write path. Re-verified post-fix: anon PATCH/INSERT rejected on both tables, the same attacker JWT now blocked, allowlisted-coach direct writes unaffected, both RPCs round-trip correctly (including upsert keeping the original row id and not letting one athlete's log touch another's row) · `npm test` green (72 tests) · **shipped to prod the same session** (client code depends on the RPCs existing — a static-only GH Pages deploy with no matching DB migration would've broken live self-log/check-in): `supabase link`, then `supabase db diff --linked` surfaced that prod's real schema (built via dashboard, never through the CLI) uses different policy names than `0001_init.sql`'s hand-reconstruction assumed — e.g. `class_executions`'s permissive-update policy is really `ce_update_anon`, not `"public update"` — so `0003`'s `DROP POLICY` statements were rewritten with `IF EXISTS` covering both names before pushing. Prod's CLI migration history was empty (schema predates the migration workflow); `0001`/`0002` marked applied via `supabase migration repair` (metadata-only, not re-executed — replaying them risked `CREATE POLICY` collisions with prod's existing same-purpose objects) so `db push` applied only `0003`. Verified against prod itself post-push (read-only/no-op checks only — no prod service-role key available to write-then-clean-up test rows): anon PATCH/INSERT denied on both tables, both RPCs resolve and execute. Surfaced a related but out-of-scope gap, filed as **#34**: prod's real `class_executions` policies also include `ce_insert_auth`/`ce_delete_auth` scoped to `auth.role() = 'authenticated'` rather than `is_allowed_user()` — since signup is open, a non-coach authenticated session can still forge/delete class rows (not an UPDATE-tampering vector, so out of `#7`'s scope, but a real gap).
